The problem

Four clouds, hundreds of releases, one migration programme

I run enterprise cloud migration programmes. That means I need to know what AWS, Azure, GCP and OCI shipped this week — not everything, just the handful of releases that genuinely change how a migration gets planned: a new database migration path, a pricing shift, a Kubernetes feature reaching GA.

The raw material exists. All four vendors publish open release feeds. The problem is volume: hundreds of announcements a week, most of them region rollouts and minor updates. Skimming four feeds is a job in itself, so like most practitioners, I mostly didn't.

A generic summary is noise. A digest filtered through your own professional question is signal.
What I built

Two commands, one briefing

/radar
Migration briefing Fetches the last seven days of releases from all four public feeds, hands them to Claude with one opinionated question — "what does this mean for migration programmes?" — and returns a digest under 250 words: the most significant item, two or three notables tagged by cloud, and one emerging pattern to watch.
/draft
Newsletter draft Reshapes the same data into a newsletter draft with markers showing where to add a personal take. The agent drafts; the judgment stays mine.
How it works

Deliberately boring architecture

01
Command received A Python service long-polls the Telegram Bot API. One command from my phone starts the whole pipeline.
02
Fetch four feeds A feed fetcher pulls this week's titles from the public RSS feeds of all four cloud vendors. Public data only — no credentials, no customer data, nothing to secure.
03
Filter through the lens A prompt builder frames the raw titles through the migration-programme lens. The prompt doesn't ask for a summary — it asks one question and instructs the model to ignore minor region rollouts. The value is the filter, and the filter is domain expertise.
04
Claude writes the digest The Anthropic API returns a structured briefing. The AI integration is about ten lines of code. The rest is plumbing.
05
Delivered to Telegram The digest travels back up the same path and lands on my phone, usually within a few seconds of the command.
Design choices

Three constraints I set before writing a line

Public data only

No tenancy credentials, no customer data, no database — the bot makes outbound calls only. There is nothing to secure because there is nothing sensitive in the system. For anyone working with enterprise clients, this is the constraint to set first.

One opinionated lens

The prompt asks one question: "what does this mean for migration programmes?" The model is instructed to ignore minor region rollouts. The value of the tool is the filter, and the filter is domain expertise — not something the model supplies on its own.

Small enough to finish

~150 lines of Python, one evening, running on my laptop. The AI part is about ten lines; the rest is ordinary plumbing. Shipped beats planned.

What I learned

The lesson wasn't technical

After nearly two decades in cloud transformation, the takeaway from this build wasn't about the code. The code is now the easy part. What makes an AI tool valuable is the professional question you point it at. Anyone can summarise a feed. Knowing which releases change a cutover plan, a licensing position, or a FinOps model — that's the part no model supplies on its own.

The other lesson: the friction is never where you expect. The AI integration took minutes. Bot tokens, environment variables and feed quirks took the evening. If you're building your first agent, budget your patience for the plumbing.
