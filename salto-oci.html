Context

What SALTO is — and why it couldn't go down

Proximus is Belgium's largest telecom operator. The Sales Handling Engine is the system where every Proximus order gets taken. It runs Siebel CRM — enterprise software from a different era, stateful, persistent, and deeply woven into the business. There is no version of this system that can be down for a weekend while things get sorted out.

The SALTO programme moved that estate in two phases: first out of the on-premises data centre and onto OCI virtual machines, then from those VMs into Oracle Kubernetes Engine. Two technology shifts, one continuous business. I led the programme end-to-end from the TCS side, spanning delivery governance, architecture, client alignment, and the teams doing the work.

The hard constraint wasn't technical. It was that 252,000 business orders had to keep flowing on the other side.
Two phases

Lift, then transform

Phase 1
Data centre → OCI
The Sales Handling Engine migrated VM-based onto OCI with business continuity held throughout. Cloud foundations laid: FastConnect, north-south firewall, landing zone, golden image and data masking. Security alignment gates passed — which later carried forward as precedent in Phase 2.
Phase 2
OCI VMs → Oracle Kubernetes Engine
The actual transformation. Both Siebel workloads — MIB (14 environments) and SHE (18 environments) — migrated to OKE. Databases upgraded 19c → 26AI on Exadata X11M. CI/CD pipelines extended through to production. All 32 environments complete.

What Phase 1 deliberately did not change: the application still ran the same way, on virtual machines that now happened to be Oracle's. Scaling was still by request. That gap is what Phase 2 was built to close.

The hard parts

What made this difficult

01
Siebel is stateful Siebel uses persistent storage, shared file systems, and a scaling ceiling set by Object Manager licence counts — not CPU. HPA max replicas are bounded by Siebel licence counts, and this has to be enforced at the platform layer, not operationally. No cloud-native autoscaling playbook covers this.
02
The OCI load balancer timeout is non-tunable The OCI LB has a 9,000ms m2 timeout that cannot be configured away. The solution was HAProxy in an Active/Passive Pacemaker cluster — introduced specifically because of that constraint. Not in any Siebel-on-OKE reference architecture, because that reference architecture doesn't exist at scale yet.
03
A legacy security posture inherited from migration Siebel↔CX integration was running over unsecured HTTP — inherited from the on-premises estate. The approach was proactive disclosure with a firm remediation date rather than silence. The principle established: proactive disclosure with a date beats silence.
04
Identity migration mid-programme Authentication moved from WebSEAL + PerID to Azure Entra ID SAML 2.0 via IDCS, with WebSEAL retained only as a legacy bookmark redirect. Each of the 32 environments required a separate Enterprise Application registration. No bulk path.
05
HAProxy failure analysis in production Under 0.1% of App X calls were failing before reaching the OCI LB. Analysis used socat stats-socket reads with no config change. Failures classified into Class A (never reached SALTO — safe to replay) and Class B (SALTO may have processed — blind retry risks duplicate Siebel records). Correlation-ID dead-lettering identified as the only safe Class B recovery path.

What I learned

The things that weren't in the playbook

Siebel on Kubernetes is not a well-documented path. Oracle runs it; a small number of large enterprises are beginning to. There is no published global count, no analyst track, and no reference architecture that accounts for the OCI LB timeout. Every decision above the generic Kubernetes layer required first-principles reasoning.

The identity migration ran in parallel with the platform migration. Two major shifts in the same programme window is a governance problem as much as a technical one — the SteerCo needed to understand what was locked and what was still moving at each week's review.

The HAProxy failure analysis was the moment that crystallised something: the failure mode matters more than the failure rate. Under 0.1% sounds small until you realise a blind retry on a Siebel order creates a duplicate record. The classification — safe to replay versus cannot safely replay — is the analysis. The number is context.

CAB is a trust test, not a knowledge test. You pass it by having already done the work, not by performing confidence on the day.
